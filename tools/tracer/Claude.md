# WHY

Local code-intelligence command-line interface for Agents working in a repository, returning dense structured facts about files, symbols, project docs, git history, and session context in one call.

# Facts

- The Rust package is named `tracer`.
- The binary is named `trace`.
- `tools/tracer` is a Cargo workspace with an `xtask` member.
- `trace` works without Claude Code.
- `doctor` verifies required external binaries.
- The external binaries are `ast-grep`, `scc`, `universal-ctags`, `ripgrep`, and `git`.
- Tree-sitter grammars are compiled into the binary.
- Per-function complexity is computed by the in-process tree-sitter decision-node walker.
- `.tracer-cache/` lives at the target repository root.
- The cache namespaces are `file/`, `sessions/<session_id>/` for the directory baseline, and `sessions/<session_id>/<agent_id>/` for that Agent's own session-context state.
- The `file/` namespace stores per-file facts, the commit index, the bulk git-activity map, the deploy-presence map, the mtime index, and the four relations entries: edges, symbols, imports, and directories.
- A cache entry holds only what its key's inputs determine.
- Every entry a schema writes, content and repo-wide alike, lives in its directory `file/schema<N>/`, and a key carries no schema.
- Every repo-wide index implements `cache::Index`: its key, how it reads its bytes into its own type, the change it needs against what is stored, how it applies a change, and whether the result is complete enough to store. `cache::index` returns the stored index when it needs no change, else takes `cache::maintain`, reads it again, and applies what is left; `cache::update` applies a change the caller names under the same lock. An incomplete result is returned and never stored.
- `memo.rs` owns every per-repo memo, so an index or map is read and parsed at most once per invocation.
- `repo_context::metrics` hands every caller one shared handle to the scc payload.
- `cache clear` empties the `file/` namespace, every schema's directory included, and `--all` removes the whole tree.
- The write that creates an index's key removes every other key of its family in its schema's directory, the keys that share its name up to a trailing `_v<N>` version, so a key that moves with repo state or a version leaves no superseded entry behind.
- `cache::maintain` is the cross-process lock `file/schema<N>/.maintain.lock` every repo-wide index update of its schema holds, so concurrent calls serialize onto one update and read its result, and a build at another schema never waits on it.
- The process that takes the lock removes every other schema's directory whose modification time is older than `stale_schema_age`, seven days, because another installed build may still run at a younger one. A directory's modification time is its newest write, because `cache::save` renames every entry into it.
- The loose entries directly under `file/` from before schema directories are one group, removed together once none of them was written for `stale_schema_age`.
- The mtime index update deletes the per-file entry it supersedes.
- The scc snapshot `file/schema<N>/repo_context_v6.json` keeps per-file rows beside the stamps they were counted at, recounts a changed or new file alone, and walks the whole tree only when an ignore file or the scc binary changes.
- A new path is tested against the tracked `.sccignore`, `.gitignore`, and `.ignore` files through the `ignore` crate, so a path the walk would skip stays uncounted.
- The per-file entry is keyed by contents and path, so it holds no git facts.
- `git_activity` owns every git fact; its disk-cached bulk map keys only history-derived facts by HEAD and the 30-day cutoff date, and is built from the commit index.
- `file/schema<N>/commits_v1.json` is the commit index: the newest `HISTORY_CAP`, 4,000, commits HEAD reaches, in `rev-list` order, each with its date, author, subject, whether it is a merge, and every file it changed with its old and new blob ids, read through `git log --raw -M --diff-merges=first-parent`, beside the blob ids known to be binary.
- A call after HEAD moves walks only the commits the index lacks, through `git log --no-walk=unsorted --stdin`, and drops every commit HEAD no longer reaches, so a rebase or reset leaves none behind.
- Working-tree state is always recomputed fresh, and deploy-branch presence is cached separately, keyed by the present deploy branches' tip commit ids.
- `git_activity::git_command` is the one git spawn in the crate; under `TRACE_TIMING` it emits `timing git <first two args>`, so a test can assert which subprocesses a call ran.
- `git_activity::blobs` is the one object reader: it streams `git cat-file --batch` and hands each object to its caller as it arrives. `git_activity::blob` reads one file at a revision through it, and `surface::rows_at` builds that file's rows from it.
- `file_facts::extraction_of` reads the declarations of a file's bytes from the per-file entry that the bytes and path key, else extracts them, so `surface::rows_at`, `diff`'s base side, and `history --contains` reuse what an earlier call extracted.
- `git_activity::activity_for` composes one path's git facts for both `for_paths` and the bulk map, so a staged rename carries the old path's history everywhere.
- The history walk and the deploy-branch `ls-tree` run with `GIT_NO_LAZY_FETCH=1`, so a partial clone never fetches from its remote for them; `blob` and every revision a command names still fetch.
- A history walk git ends early is a floor, and it and a presence map with a failed listing are never stored.
- `git_activity::for_paths` answers a batch's working-tree state from one tracked-only `git status --porcelain=v1 -z --untracked-files=no`; `bulk_cached` keeps the full scan for `status` and the primer.
- A warm file call spawns three git processes side by side: `status`, `rev-parse HEAD`, and `for-each-ref`. A warm `stats` spawns none.
- `cache::worktree_root_for` walks up to the nearest ancestor holding a `.git` directory or a `gitdir:` file and spawns nothing; a path inside a `.git` directory resolves to `None`.
- `repo_files::tracked_files` is the one freshness gate. `file/schema<N>/tracked_files_v1.json` stores every path with whether git tracks it, beside the four-field stamps of every walked directory, every ignore file read, and the git index; a warm call restats those stamps and reuses the stored listing when every one matches.
- A stamp mismatch runs discovery under `cache::maintain` with `git ls-files` beside the full status; a directory stamped within two seconds of that run is stored as unstable and rechecked on the next call.
- `TRACE_TIMING=1` prints one line per phase to stderr on any command, in microseconds. No flag changes output without it.
- `file_facts::with_git` joins the git facts onto per-file facts on every resolve.
- `relations.rs` owns the two inversions and the on-demand resolver.
- The inversions are `name -> {defined_in, used_in}` and `file -> [importer]`.
- `file/schema<N>/relations_edges_v1.json` holds the file table, provenance, and importer inversion; `file/schema<N>/relations_symbols_v1.json` holds the name inversion and is parsed only for a symbol query; `file/schema<N>/relations_imports_v1.json` holds every file's import rows beside the inline `mod`s it declares, each `mod` with a body, with its name and the lines from its header to its end, and the Rust types it declares, each with its innermost inline `mod`, and is parsed only for an update, for a Rust type path, whose type and whose candidates' `Self` types it reads, for a Rust path with segments past the file it reaches, for a Rust reference that follows a `use` out of a position other than its bare-name start that declares no target it can reach, or for a Rust reference whose bare-name start declares its name while a `use` in force at the call binds that name, or is a `*`, from inside a block.
- `file/schema<N>/relations_directories_v1.json` holds the per-directory metrics; it is written on an index update and read by `directory_metrics`, memoized once per process.
- `relations::Roots` holds the root mappings, each Cargo package's crate names, each with the library root it reaches, and each package's left-out names, each with the library roots it may reach, and each directory `tests/Pest.php` binds to the test case class its closures run as. `Roots::read` reads `composer.json`, `tsconfig.json`, `jsconfig.json`, and `tests/Pest.php` on every index check, and stores `Roots` in the edges entry, so no query reads a manifest.
- `php::pest_bindings` reads `pest()->extends(X::class)->…->in(…)` and `uses(X::class, …)->…->in(…)`, each directory relative to `tests/`.
- Each listed `Cargo.toml` is parsed through the `toml` crate and stored in the edges entry beside its stamp from `repo_files::tracked_files`; a check reads only a manifest whose stamp moved.
- A changed root mapping re-resolves the import rows of every file in the languages whose mapping changed and re-absorbs no file; a manifest change that moves no mapping, such as a version bump or a new dependency from outside the repository, rewrites the edges entry alone.
- Rust's mapping is its crate roots, each package's crate names that reach a library of the repository, and each package's left-out names.
- The root mappings are PHP's PSR-4, TypeScript's `paths` and `baseUrl`, and Rust's crates.
- An import in a language that has a root mapping, matching no root and not relative, resolves to nothing and records no edge. It is external, so a reference through its binding resolves to nothing, unless it is a Rust import that is not proven external. A Rust import whose first segment is a left-out name records an `INFERRED` edge to the files the rest of its path names in each library that name may reach; `ModulePaths::rust_path_within` reads that rest for both the import and `crate_scope`.
- Symbol fallback runs only when the language has no root mapping in this repository.
- A file never imports itself.
- PHP resolves `module\symbol` through PSR-4, then `module` alone. Case is compared exactly.
- A PHP `use X\Y as Z` binds `Z`, so a class named `Y` in the importing file is never read as a reference through the import.
- TypeScript and JavaScript resolve relative, then the longest `paths` prefix, then `baseUrl`; each candidate is tried as `.ts`, `.tsx`, `.js`, `.jsx`, then as a directory holding `index.<ext>` in the same order.
- A `Cargo.toml` with a `[package]` is a crate. Its library root is the `[lib]` path or `src/lib.rs`, named by `[lib] name`, else by the package name with `-` read as `_`. Its binary roots are `src/main.rs`, `src/bin/*.rs`, `src/bin/*/main.rs`, each `[[bin]]` path, and `src/bin/<name>.rs` for a `[[bin]]` with no path. A root counts where its file exists.
- A Cargo package's crate names are its own library's name and one name per key of its `[dependencies]`, `[dev-dependencies]`, `[build-dependencies]`, and the same three under every `[target.*]`. A package's workspace root is the nearest manifest at or above it that holds `[workspace]`, else its own manifest. A `{ workspace = true }` key reads its entry in the workspace root's `[workspace.dependencies]`.
- An entry with a `path` reaches the library root of the package that path names. Any other entry reaches the library of its workspace root's `[patch]` entry whose source and package match its own. An entry that names no library of the repository either way reaches no root. An entry with no `path`, matching no `[patch]`, whose package, its `package` value else its key, is the name of a package of the repository, whatever its workspace root, is left out of the package's crate names, because a redirect tracer does not read may lead there, so it is never proven external. A left-out name is the library name of each package of that name, or its key with `-` read as `_` for an entry renamed with `package`, and may reach that package's library.
- An entry's source is its `git` URL, else its `registry`, else `crates-io`. `relations::canonical_source` reads an entry's source and every `[patch]` key the way Cargo compares them. No source, `crates-io`, and `https://github.com/rust-lang/crates.io-index` are one source. A source drops a trailing `/`. A URL lowercases its scheme and its host, the part after any `@`, and drops a trailing `.git`. On `github.com` it reads as `https` with its path lowercased.
- A `[patch]` entry matches the package its `package` value names, else its key.
- A `registry = "<name>"` source matches only `[patch.<name>]`, never a `[patch]` keyed by that registry's index URL, because the name maps to its URL only in `.cargo/config.toml`, which tracer does not read.
- A `[patch]` in `.cargo/config.toml` is not read, so a crate it redirects into the repository is reached through its left-out name.
- A key is named, as Cargo names it, by the library it reaches, and a left-out key by the library it may reach. A key with a `package = "…"` rename, or one that reaches no library, is named by itself with `-` read as `_`.
- A Rust file belongs to the package whose directory holds it most closely.
- A Rust crate root is its own crate. Any other Rust file's crate root is the root whose directory holds it most closely; a file no root's directory holds, such as a test or a build script, is its own crate root.
- A Rust path resolves inside the file's own crate: `crate::`, `self::`, and `super::` start at the crate root, the file's module, and its parent; a bare first segment is a child module of the file, else the path through each `use` of the file that binds it, one hop, else the library root a crate name of the file's package reaches, which is the only crate a package's file reaches by name, or for a file no package holds the libraries of the repository of that name nearest it, else a module `X::<first>` that a `use X::*` of the file brings in, else no file. The path descends `a/b.rs` or `a/b/mod.rs` and names the deepest module file it reaches.
- A Rust file's module is read from the file that declares it: a `mod` item with `#[path = "…"]` names that file, joined to the declaring file's directory, and its module is the declaring file's module and the `mod`'s name, so `super` inside it reads from the declaring file. `Declaration::module_file` carries the `#[path]` value, and `Built` keeps each file's `#[path]` modules in the edges entry.
- `ModulePaths::rust_path` follows a `use` at the top level of a file it reaches that binds the first segment left past that file, one hop, so after `pub use engine::config;` in `lib.rs`, `crate::config::Builder` and `crate::config` name `engine/config.rs`. The hop counts when it leaves fewer segments or reaches another file, so after `pub(crate) use client::legacy_core;`, `crate::legacy_core::config::edit::Builder` names `client/src/lib.rs` with `legacy_core::config::edit::Builder` left, its inline `mod`s and the type, and the walk follows the `*` in `edit` from there to the declaring file. `ModulePaths::rust_item_path` reads a `use` row's path, an import's, and a type path, whose last segment is an item the walk follows itself, and takes that hop only for a segment with another after it.
- Rust `use a::b` is resolved as the path `a::b`, so `use crate::summary::Facts` names `summary.rs` and `use crate::{summary}` names `summary.rs` too.
- A Rust path is written the way the file's own module reads it: `Self` is the enclosing impl's type, an inline `mod` is part of the file, so the leading `self`, each `super` that leaves an inline `mod`, and each segment after them that names an inline `mod` of the module reached become one `self`, and a `use` alias is the path it stands for, so an aliased call is the path call it names.
- A Rust macro's arguments are parsed as a tree of their own that continues outward from the invocation, so `self`, `Self`, a parameter's type, and `super` inside them read the way they read beside the macro.
- A Rust path is external only when its first segment, after the file's own `use` binding, is `std`, `core`, `alloc`, `proc_macro`, or `test`, or a crate name of the file's package that reaches no root.
- Under crate mapping a Rust free call starts in its own file at the innermost inline `mod` holding the call, which `use_sites` finds once through `surface::innermost`, else at the file's top level; a path call starts in the module it names as a free call, and a path that names a type is a type path. A segment past the file the path reaches names an inline `mod` only when that file declares an inline `mod` of that name, and is a type otherwise, so `nested::imp::start()` is a free call that starts at `imp` in `nested.rs` whatever `imp` declares, and `engine::Thing::new()` is a type path. A free path the walk proves external, such as `std::process::exit` written out or reached through a `pub use`, resolves to nothing, not even in the calling file. A path whose first segment, after the file's own `use` binding, is a left-out name of the file's package reaches every file of the libraries that name may reach as a free call when the rest of the path names a module of that library, and resolves there `INFERRED`.
- A Rust type path's candidates are the methods whose `Self`, the type their `impl` names, resolves to the type the path resolves to, in any file of the repository, and the type itself. `Declaration::self_type` carries `Self` as written, and `relations::resolve_type` reads both sides the same way, where each is written: a one-segment path walks from where it is written through the `use` items in force there, a longer one from the files its path names, and the walk stops at a declared type. A type's identity is `TypeKey::Declared`, the file and name of its declaration; `TypeKey::Unreached`, a dead end of the walk, a module position a path or a `use` that binds the name led to where it found no declaration, so two paths that end at the same dead end still match; or `TypeKey::Outside`, a type outside the repository by the name the walk last looked for, such as `Url` or the prelude's `String`. A candidate resolves at the weaker of the two sides' confidences, and an `Outside` side is always `AMBIGUOUS`, so an `impl From<Location> for Url` is a caller target of `Url::from(…)` and never `EXTRACTED`. A `container` stays as written.
- `use_sites` resolves the candidates' own types once per query into `TypeOwners`, each identity with the candidates that have it, and each Rust type path once per file into `TypePaths`, keyed by its inline `mod`, its text, and the imports in force, so a type path costs one walk per file and one lookup per identity, and `TRACE_TIMING` prints one `own_types` line per query and one `resolve_type` line per walk.
- `ModulePaths::crate_roots` reads a file's crate roots from its nearest ancestor directory that holds one, through `crate_directories`, never by testing every root.
- `ModulePaths::files_named` looks a path up in `Relations::built_from`, never by testing every file, so a TypeScript import's nine candidate paths cost nine lookups.
- Every `use` in force that binds a name counts, as under `cfg` alternatives: `relations::path_after_binding` returns the path through each, `crate_scope` and `resolve_type` start from each, and the extractor's alias reads a name only when one `use` binds it.
- A Rust `type Name = path;` outside an `impl` or `trait` is an import row of `path` bound as `Name`, so the walk follows a type alias as it follows `use path as Name`, and it counts as an import edge.
- Crate-scoped resolution may raise a Rust reference's confidence and never removes a candidate the name rule would list: a reference whose scope yields no candidate falls to the name rule at most `INFERRED`, and only a path the walk proves external, where no declaration of the repository can be the target, stays unresolved.
- The name rule resolves a path by its last segment against every same-language candidate whose shape matches, as it does without a crate mapping. A Rust path that matches no candidate's type there resolves as the free call of a module path when its first segment names a module of the repository: `crate`, `self`, or `super`, a `mod` the calling file or a candidate's file declares, or a module file of that stem. Any other such path stays a type path, so `Vec::new()` reaches no free `new`.
- That free call keeps only the candidates in a module the path names: every candidate for a path that starts with `crate`, `self`, or `super`; a candidate in the module files `rust_path` names for the path, read through the `use` in force that binds its first segment, when `relations::admits` accepts it at the module `relations::named_module` reads from the segments past those files in its file, the one module rule `crate_scope`'s positions read, so a path into a crate admits only the files it names there, never another file of that crate, a path that names only a file admits only its top level, and a type path such as `config::Config::load()` admits no free `load`; `use_sites` works those files out once per call; and only for a path that names no file, such as in a repository with no `Cargo.toml`, a candidate whose module, its enclosing inline `mod` else its file's stem or its `mod.rs` directory, is the path's last segment. `relations::Candidate` records its enclosing inline `mod`, so a file imported for another reason never takes the call. A candidate kept only because the path starts with `crate`, `self`, or `super` takes no confidence from an import or from the calling file, so it resolves at most `INFERRED` wherever it sits.
- A Rust `use` of an inline `mod` of its own file, such as `use outer::inner;`, imports `self` bound by its alias, else by its module name, so `inner::deep()` is the path call `self::deep()`.
- Rust resolution walks modules: each position is a file and the inline `mod` inside it that the position stands for, else its top level, and a declaration counts at a position only when its innermost inline `mod` is that module. A path or a `use` reaches the inline `mod` its last module segment names inside the file it reaches, where a module segment is one of the leading segments past that file that name an inline `mod` the file declares, so `use crate::engine::imp::start` reaches `imp` in `engine.rs` and `use crate::engine::start` reaches the top level of `engine.rs`. A `*` over a type, such as `use engine::Kind::*` over an enum, reaches no position, because it brings in only the type's variants and associated items. From each position the walk follows each `use` item of that module that binds the name and each `*` import, one hop at a time until a position declares a target the call's shape can reach, so a `pub use` re-export and a glob reach the declaring module and a same-named method, or a namesake in another `mod` of a file the walk passes, stops no free call; nothing outside the positions reached is a candidate. Only the bare-name start, where a free call or a one-segment path starts at the call, follows the `use` items in force at the call, the calling function's own included, because in Rust only a bare name sees them. When one of them that binds the name sits in a function body and its path names no module of the repository, by `relations::named_module`, the start neither stops on its own declaration of the name nor counts it, because in Rust a function's own `use` hides a same-named item of its module in the namespace it binds. A `use` of a module binds the module namespace alone, so it hides no function. When a `*` in force at the call sits in a function body, the start counts its own declaration and still follows the glob, because the glob's names are known only where it leads, and in Rust a function's own glob outranks its module's items. Two limits are accepted: a `use` of a standard-library module still hides, because tracer cannot tell a `std` module from a `std` function, and a `fn` declared in a nested block counts as an item of its module. The start is a flag on the position, never its file and module, so a path's start and every hop, a hop back into the calling module included, is a position of its own: it follows only the stored module-body rows of its file, each row owned by the module whose own body holds its block: a top level owns the rows outside every block, an inline `mod` owns only the rows in that `mod`'s own body, those whose innermost inline `mod`, which `surface::innermost` finds from the stored lines of each inline `mod`, is that `mod` and whose block ends on that `mod`'s end line, and no module owns a row in a function body. A position follows the rows its module owns, so a `use` inside a function is never followed past the bare-name start, and a position that counts every declaration of its file follows every module-body row. A hop's `rust_path` reads its first segment through the globs of its position's followed rows alone, never a sibling module's. A path that starts with `self` and stays in the file that wrote it, such as `inner::deep()` or `use super::shapes::helper` from a sibling inline `mod`, counts every declaration of that file, because the extractor folds the inline `mod`s such a path names into `self`. A hop whose path starts with a left-out name adds every file of the libraries that name may reach as `INFERRED`, every declaration of them counting, a `use` that binds the name and whose path is external proves the reference external and records the name it leads to as outside the repository, a `*` whose path is external proves it only when the walk left no dead end, a position a path or a `use` that binds the name reaches that declares nothing and leads nowhere, because a dead end may still hold the name, and a hop whose path names no other file and is not external sends the reference to the name rule. `relations::walk_modules` is the one walk, for a free call and for a type path alike.
- `extraction::Import::block` is the first and last line of the `mod` body or block that holds a Rust `use`, and none at the top of a file. `Import::in_force` is the one binding lookup: an import binds at a line its block holds, unless a smaller block holding that line binds the same name. The invalid binding of an external import, `crate_scope`'s receiver binding, the walk at the bare-name start, the name rule's module files, and the extractor's aliases read only the imports in force at the reference's line. `relations::path_after_binding` is the one reader of a path through the `use` items that bind its first segment.
- A Rust `use` binds its alias, else its symbol: the walk follows a `use … as Local` by `Local` and continues by the name it renames.
- The stored confidence for a (target, importer) pair is the strongest of the pair's rows: `EXTRACTED` over `INFERRED` over `AMBIGUOUS`.
- `extraction::Declaration` carries `name`, `kind`, `header_line`, `line`, `end_line`, `container`, `parent`, `header`, `is_abstract`, `is_data_shape`, `annotations`, for Rust `self_type` and `module_file`, and for a PHP class, interface, trait, or enum `supertypes`, its traits, then its parent, then its interfaces, each by its last segment; `kind` includes `property` for a PHP property, promoted parameter, and enum case, and a TypeScript field.
- `header` is the declaration's own source text, sliced by the extractor from byte ranges of the file: attributes, decorators, modifiers, kind keyword, name, generics, parameters, return type, heritage, and initializer, with every body elided at its AST node.
- `header_line` is the first line of the header and `line` is the name's line, so a window holding only the attribute above a method still selects that method.
- `parent` is the index of the lexical parent row in the same file's declaration list.
- A property is never a reference target, so `defines` answers for it while `callers` and `usages` exit 2.
- The extractors are the one declaration parser; `signatures.rs` is deleted and no command reparses a file to render a row.
- `extraction::extract` falls back to `universal-ctags` for a language no tree-sitter extractor covers: it writes the bytes to a temporary file under `<root>/.tracer-cache/tmp/` and runs `ctags --output-format=json --language-force=<lang>` on it at cache build or update, and for a file at a revision that `surface::rows_at` or `history --contains` reads.
- `file/schema<N>/ctags_maps_v1.json` stores the extension map from `ctags --list-maps`, stamped with the ctags binary's path, size, and modification time, so a warm call spawns no ctags at all.
- `ctags_denied_languages` drops the data and markup formats whose tags are keys rather than declarations, and `ctags_denied_kinds` drops `heredoc`.
- `Built` carries one count per annotation name for each file, over one interned name table in the edges entry.
- `DirectoryMetrics` counts a directory's direct files only: `imported_by` is the distinct outside files importing them and `imports` the distinct outside files they import; an `AMBIGUOUS` row and a same-parent edge count for neither.
- `context`, `read`, `status`, `diff`, file `info`, and `grep` pass `module_counts` to their facts because they already load the relations index; `pattern` and `blame` do not.
- The front matter's `directory` block is built from one `read_dir` and the directory-metrics memo, never from a per-file facts resolve; `record_read` records coverage.
- `ShownRecord::shown(kind, key, value)` is the one gate for what text output shows an Agent once per context: it compares `value` with the value that Agent was last shown for `(kind, key)` since its last context reset and returns `New`, `Same`, or `Changed` with only the lines that changed, and keeps `value` unsaved in the record unless it is `Same`. Without a session it always returns `New`.
- A record is saved only after the text it describes is flushed: the caller flushes stdout, then calls `ShownRecord::save`, and a record dropped unsaved writes nothing, so a call killed or cut off before its output arrives records nothing as shown.
- One record gates one file's `Listing` and `Facts` and saves both in one write; a command that prints several files gives each file its own record and saves it after that file is flushed.
- `Changed` diffs the top-level keys and one level inside a mapping, the lines `yamlfmt::block` prints; anything deeper is one line, a removed line is `null`, and a value that is not a mapping on either side is only ever `New` or `Same`.
- The value passed to `shown` is shaped as the front matter prints it, so each `Changed` line is one printed line: `directory_facts` passes `{directory: <block>}` and prints `lines["directory"]`, so a moved `at_session_start` prints whole.
