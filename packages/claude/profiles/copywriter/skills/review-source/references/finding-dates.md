SOP for extracting Published/Updated dates, verified against live pages (css-tricks, Guardian, TechCrunch, Cloudflare RSS, Wayback CDX, Reddit, static sites). Precedence order first, then per-method findings with observed evidence.

## Ordered method list (run top to bottom, stop when both dates found; always run step 7 as a sanity check)

1. **JSON-LD `datePublished` / `dateModified`** (in `<script type="application/ld+json">`, often inside `@graph`). Best structured source: full ISO timestamps with timezone, present on nearly every CMS (WordPress/Yoast emits it by default). Verified on Guardian and css-tricks, where both fields were present and matched the meta tags. Parse all JSON-LD blocks; the `Article`/`NewsArticle`/`BlogPosting` node is the one that counts.
2. **Open Graph article meta tags** — `article:published_time`, `article:modified_time`, `og:updated_time`. Equally common, same values as JSON-LD in practice (verified identical on both test articles). Use as confirmation of step 1 or as fallback. `og:updated_time` alone is weak: some themes stamp it with render time.
3. **Visible byline / `<time datetime="...">` elements.** Grep for `<time` with a `datetime` attribute, then for byline patterns near the top of the article: "Published", "Updated", "Last updated", "Posted on", `\b(Jan|January...) \d{1,2}, \d{4}\b`, ISO dates, and relative dates ("3 days ago" — resolve against fetch date). This is what the reader sees, so it is what the site is accountable for. It is also the only signal on many older or hand-built pages. Caveat: often date-only (no time), locale-ambiguous formats (03/04/2024), and sites showing only "Updated" while hiding the original publish date.
4. **URL date pattern** — `/2024/03/`, `/2026/jul/23/`, `-20240314`. When present it is the publish date and essentially never lies (it is baked into the permalink; Guardian and TechCrunch both use it, and Guardian's URL date matched its `datePublished` exactly). Gives Published only, month or day granularity, never Updated.
5. **RSS/Atom feed** — `<pubDate>` / `<atom:updated>`. Reliable timestamps (verified on Cloudflare's `/rss/`), but only covers the newest ~10–20 posts. Useful when the article page itself is JS-rendered or paywalled. Find via `<link rel="alternate" type="application/rss+xml">` or guess `/rss`, `/feed`, `/atom.xml`.
6. **Sitemap `<lastmod>`.** Fetch `/sitemap.xml` (follow `sitemap_index.xml` to per-post sitemaps; verified working on css-tricks) and find the URL's entry. Good Updated signal at day granularity. Caveats: many sitemaps regenerate `lastmod` wholesale on deploy (a whole sitemap sharing one recent date is the tell), and large sites shard sitemaps so finding the entry costs several fetches.
7. **Wayback Machine as verifier and lower bound.** `http://archive.org/wayback/available?url=<u>&timestamp=1990` or the CDX API (`web.archive.org/cdx/search/cdx?url=<u>&limit=1&fl=timestamp`) returns the first capture in one call, no auth. Use it two ways: (a) first capture as an upper bound on the true publish date when nothing else exists, and (b) as a lie detector for suspiciously fresh metadata. This caught a real lie in testing: css-tricks' "A Guide to Flexbox" declares `datePublished: 2026-05-28` in both JSON-LD and meta tags (the CMS restamped it on a recent edit), while Wayback's first capture is 2013-06-03. If claimed Published is much newer than first capture, report first-capture year as Published and keep the claimed date as Updated.
8. **Platform APIs when the source is a platform.** Reddit: `created_utc`/`edited` from the JSON API — but note unauthenticated `.json` requests are blocked from datacenter IPs (got 403/HTML wall in testing); OAuth or a browser session is needed. YouTube (`publishedAt` in page JSON), Hacker News (Algolia API, `created_at`), Stack Exchange API, review platforms (G2/Trustpilot render dates in JSON-LD `Review` nodes) all beat scraping the rendered page.
9. **HTTP `Last-Modified` header — last resort, Updated-only, low trust.** Meaningful only on truly static files (static-site generators, ziglang.org returned a plausible one). On any CMS/CDN it reflects cache or render generation, not content: css-tricks returned `Last-Modified: Fri, 17 Jul 2026` for a 2013 article behind Cloudflare. Trust it only when it is old (a stale date is honest; a fresh one proves nothing) and when no HTML-level signal exists.

## Cross-cutting rules

- **Prefer agreement over any single source.** Two independent signals agreeing (JSON-LD + visible byline, or URL date + meta) is the confidence bar. Record which methods produced each date.
- **The systematic lie is restamped freshness**: CMSes and SEO themes rewrite `datePublished`/`published_time` on edits or theme changes to game "freshness" ranking. Wayback first-capture (step 7) is the only cheap defense; run it whenever Published looks recent for evergreen content.
- **Published missing, Updated present** is acceptable per the pipeline requirement, but record Wayback first capture as the Published lower/upper bound anyway.
- **Granularity**: keep dates as found (day vs full timestamp); never invent precision. Normalize to ISO 8601, keep the source timezone.
- Fetch with a browser User-Agent; several sites (TechCrunch, Reddit) gate default curl agents.
