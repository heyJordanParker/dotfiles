# WHY

Prompt building-block workspace where each file type owns exactly one kind of Prompt block: Frame, Skill Process, Command, or Hook.

# Facts

- `agents/<agent>.md` carries frontmatter, one Frame, and Principles.
- One `agents/<agent>.md` is the whole Agent, dispatched as a Claude Subagent by that name. This holds for a profile's own Agents under `packages/claude/profiles/<name>/agents/` too.
- Interactive codex runs as the CTO: `config.toml`'s `model_instructions_file` points at `cto.prompt.md`, which `scripts/agents.py` generates from `agents/cto.md`.
- The Harness's own per-Agent memory (`memory: user|project|local`, `~/.claude/agent-memory/<name>/`) is switched off by `autoMemoryEnabled: false` in every root, the default one and each profile.
- `memory: none` in an Agent's frontmatter denies it Memory on a Claude Subagent dispatch; omitting the key leaves Memory reachable.
- Memory is Honcho, reached through the `honcho` command in `packages/bin/`, which wraps `lib/honcho.py`. There is no memory MCP server on either Harness.
- Memory is stored one peer per human and one per agent, all inside one session per repository, and no peer observes another: each peer's collection holds Honcho's conclusions about that peer's own messages, so nothing is derived twice.
- `remember_architect_message.py` and `remember_agent_message.py` write the messages and `remember_tool_use.py` writes one `[work]` line per Write/Edit/Bash/Agent call, so memory holds what an Agent did and not only its account of it; reads are excluded because `trace` records those per file.
- `inject_honcho_memory.py` reads the architect's collection and the running Agent's — unsearched at `SessionStart` and `PreCompact`, searched on the turn's own words at `UserPromptSubmit`, and skipped entirely for an acknowledgement or a slash command. The architect's block opens with his peer card, the part that does not depend on the turn matching a conclusion. Each retrieval is capped well under the write timeout and falls back to the last answer that arrived, so a slow server makes a turn stale rather than blind; an answered "nothing stored" is not a failure and clears that fallback. `lib/event.py`'s `agent_name` names the running agent from `agent_type` on both Harnesses.
- No prompt event fires inside a Claude Subagent, so the same Hook reaches one through its dispatch: on `PreToolUse` for the `Agent` tool it prepends the dispatched Agent's own Memory and the architect's to the brief through `updatedInput`, keyed off `subagent_type` so the peer is the Agent about to run rather than the one dispatching it.
- `honcho context` returns stored conclusions, `honcho search` the messages behind them, and `honcho ask` Honcho's own reasoning over a peer in prose. A question about what was decided is a `search` or an `ask`.
- `honcho remember <text>` keeps one thing in the running Agent's own collection, and never takes an Agent name — a name is the one thing an Agent would get wrong. `CLAUDE_CODE_AGENT` names a Claude session.
- Inside a Claude Subagent `CLAUDE_CODE_AGENT` holds the dispatching Agent, so `name_memory_caller.py` names the Subagent from the `PreToolUse` payload, which both Harnesses carry. On Claude it writes `--as <agent>` into the command through `updatedInput`, verified live, and carries no `permissionDecision`, so it grants nothing another gate would refuse. codex discards an `updatedInput` carrying no `permissionDecision: allow`, and that grant would approve the call over every Hook ordered behind it, so a codex Subagent is refused and told to name itself instead. A call the rewrite cannot reach — one behind an environment prefix — is refused the same way.
- `memory: none` denies an Agent Memory in every direction: `block_memory_access.py` refuses the `honcho` command on both Harnesses, `inject_honcho_memory.py` injects nothing, and `remember_agent_message.py` stores nothing. All read the declaration through `agent_memory.definition_path`, which resolves an agent codex spawns and a Claude Agent by name under the active config root.
- Both enforcement points read the declaration through `lib/agent_memory.py`, which honours quoted and commented spellings and treats an unreadable definition as a denial.
- `readonly: true` in an Agent's frontmatter takes writing away from it on both Harnesses: the write tools, every shell command that changes the tree, and output redirection. Omitting the key leaves it writing. `block_denied_access.py` enforces it, reading the declaration through `lib/agent_memory.py`, where an unreadable definition denies.
- `mode: orchestrate|build|interview` in an Agent's frontmatter names how it works: `orchestrate` spawns Subagents and mutates nothing, `build` writes and spawns nothing, `interview` neither writes nor spawns. Every Agent in the roster declares it, so the omission fallback, `build`, never decides a real dispatch. `lib/session_mode.py` resolves it on both Harnesses through `lib/agent_memory.py`, and `block_writes.py` and `block_spawning.py` enforce the two surfaces.
- A dispatch is a Claude Subagent, so it works under its own `mode` rather than its dispatcher's. `session_mode.is_dispatched` reads `agent_id`, which Claude sends only inside a Subagent call, and nothing else. The architect's sessions started with `--agent` carry `agent_type` without `agent_id`, so they stay his.
- `classify_intent.py` names the mode Skill from `session_mode.resolve`, so the Skill an Agent loads and the mode the gates enforce come off one policy.
- The spawn surface answers to the mode `session_mode.resolve` names, in every session: a dispatched Agent's declaration, the Agent a session runs on, or the mode the architect typed. A session that names no Agent and typed no mode has no chosen mode to enforce and spawns.
- Every write answers to the launching session's state axis, so a main session is held back by `propose` and let through by `execute` whatever mode it records, and a dispatch inherits its launcher's: a Subagent under a proposing session writes nothing in the tree. A dispatch with no recorded launcher runs as `execute`.
- An orchestrating Agent is refused mutations, not Bash: `block_writes.py` runs the same target parser on its commands, so a read-only check like the suite, `ls`, or `git status` runs and only a command that changes the tree is refused.
- `ssh: enabled` is the one opt-in declaration: absent, an Agent cannot reach another machine (`ssh`, `scp`, `sftp`, `rsync`, `mosh`, `telnet`), because the architect is the only one who touches production. It is independent of `readonly`, so an Agent can read a machine and change nothing.
- The shell half of both is an allowlist, not a denylist: a read-only Agent runs the commands in `block_denied_access.py`'s `_READERS` and nothing else, and a line the guard cannot parse blocks. A denylist fails open on the first shape nobody listed, and `env X=1 sed -i`, `bash -c '…'`, and an absolute path are each one line. No runtime or package manager is on that list — `python3`, `uv`, `npm` and `make` run whatever they are handed — so an Agent that must execute the suite does not declare `readonly`.
- `lib/command.py` is the single reader of a shell command line: `invocations` resolves every command a line runs, past `env`/`sudo`/`timeout` prefixes, absolute paths, extra lines, and `bash -c` nesting, and returns None for a line it cannot parse. `block_denied_access.py`, `block_spawning.py` and the other command guards decide from it rather than from the raw string.
- A line whose program is not in the line reads as unparseable, so one rule closes every guard at once: inline runtime code (`python3 -c`, `node -e`, `-m`), a program piped into a runtime, a script file that is not our own tooling, `source`/`eval`, a head the shell expands (`$SHELL`, backticks), and `alias`/`function` all answer None. `hides_execution` decides it and `OUR_TREE` is the trust boundary — a script under `/dotfiles/`, `/.agents/` or `/.claude/` is ours and runs, so `python3 scripts/sync.py` works and `sh /tmp/x.sh` does not. A runtime running its own flags names no program, so `python3 --version` reads normally.
- A command carried inside another one is read rather than refused: a shell's `-c` string, an `ssh` line, a `find -exec` command, and a command behind `do`/`then`/`if` all resolve by name, so `for f in *; do claude -p y; done` reaches the spawn gate as `claude`.
- A script named in a manifest stays trusted, so `make test`, `npm run lint` and `bun run build` are read as the runner, never as the recipe behind it. A recipe can carry anything, and refusing them would refuse ordinary work in every repository.
- `tools:` is the Harness's own field, honoured natively by Claude and dropped from the codex artifacts, so `block_denied_access.py` also refuses the write tools on codex to an Agent whose `tools:` names none — the same answer Claude reaches by never offering them. An Agent with no `tools:` line has every tool on both Harnesses.
- An agent codex spawns is gated by the role codex names on the payload as `agent_type`, and a role with no definition, such as codex's own `default` and `worker`, runs as `build`. An interactive codex session names no Agent and is never gated by a declaration. Our roster is not published as codex roles: a role backed by a `config_file` fails to apply in codex 0.153.4, so a role file would govern nothing and would shadow codex's own.
- Commands live in `commands/<command>.md`.
- `skills/<skill>/SKILL.md` is a Skill manifest and its Process.
- References live in `skills/<skill>/references/<process>.md`.
- `hooks/<module>.py` is the shared Python Hook source.
- `scripts/agents.py` generates Codex Agent artifacts from `agents/<agent>.md`.
- `scripts/hooks.py` generates Hook wiring from each Hook's `BINDING`.
- A `BINDING` declaring `roots: "all"` is generated into every profile's `settings.json` as well as the default root's.
- The Hooks bound to one event and tool run in one `hooks/combine_hooks.py` process, which feeds each the event and merges their refusals, context, and one input rewrite into one answer.
- A `BINDING` declaring `standalone: True` keeps its own process: the Hooks that inject large context or call the network or a model.
- A Hook's injected context stays under `lib/feedback.py`'s `CONTEXT_LIMIT`, 10,000 characters, because Claude Code replaces a longer hook message with a 2,000-character preview.
- The `/cc` Skill is the Process for writing Prompts.
